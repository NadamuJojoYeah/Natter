## 2. 健康状态语义（新功能）

这次把原来混在一起的 `degraded` 拆成四档：

| status | 含义 | 该做什么 |
| --- | --- | --- |
| `healthy` | 一切正常 | 无 |
| `plugins-failed` | 核心正常，但有插件没起来（多为缺配置） | 配好或移除那些插件 |
| `degraded` | 核心能力受损（上游断开 / Tier1 provider 不可用） | **立即处置** |
| `unknown` | 没配上游，无从判断 | 检查配置 |

### 2.1 验证状态判定

```bash
# 当前应为 plugins-failed（3 个插件缺配置，但 Discord 正常）
curl -s http://127.0.0.1:5099/health | jq -r '.status'
```

**判定要点**：`status=plugins-failed` 同时 `upstreams[].connected=true` → 这是**正常状态**，不是故障。

如果看到 `degraded`，那才是真问题，去查 `upstreams[].connected` 和 `providers[].available`。

### 2.2 验证退出码

```bash
sudo bash -c 'set -a; . /etc/natter/live.env; set +a; /opt/natter/natter health --json' >/dev/null 2>&1
echo "exit=$?"
```

| 退出码 | 含义 |
| --- | --- |
| 0 | healthy |
| 4 | degraded（核心故障） |
| 5 | plugins-failed（插件缺配置） |

预期当前是 **5**。

> 为什么 `plugins-failed` 不给 0：给了 0 自动化就完全看不见「有插件没起来」。给独立码之后，只想看故障的脚本比对 `4` 即可。

## 3. 三个修复的验收

### 3.1 分片超长（emoji）

**这个必须用真实平台测**，因为缺陷本质是平台拒收。

在 Discord 里发一条包含长 emoji 序列的消息让 bot 回显，或直接让 bot 输出：

```text
测试消息（复制发给 bot）：
请原样重复下面这段，不要省略：
👨‍👩‍👧‍👦👨‍👩‍👧‍👦👨‍👩‍👧‍👦👨‍👩‍👧‍👦👨‍👩‍👧‍👦🇨🇳🇨🇳🇨🇳🇨🇳🇨🇳
```

**判定**：消息完整送达、无报错、无丢字。

修复前的症状是**Discord 直接拒收**（`sendFailures` 会 +1），而且日志里是 400 错误。

```bash
# 查是否有发送失败
curl -s http://127.0.0.1:5099/health | jq -r '.upstreams[] | "sendFailures=\(.sendFailures) lastSendError=\(.lastSendError)"'
```

**验收标准**：`sendFailures` 保持 0。

### 3.2 markdown 围栏跨片

让 bot 输出一个长代码块（超过一条消息上限，Discord 约 2000 字符）：

```text
测试消息：
请输出一个 150 行的 C# 代码块，每行都是 Console.WriteLine("line NNN");
```

**判定**：分片后每一片都是**独立完整的代码块**——即每片自带 ```` ``` ```` 开头和结尾，Discord 里渲染成多个代码块，而不是「一段代码 + 一段纯文本 + 一段代码」。

修复前的症状：第一片没有闭合围栏、中间片是纯文本、最后一片没有开头 → 渲染全乱。

### 3.3 `--no-host` 对插件命令

```bash
# 宿主正在运行时执行（关键：必须先确认 natter.service active）
systemctl is-active natter
/opt/natter/natter web status --json --no-host
```

**判定**：

```text
修复前    exit 3, error: HL-CLI-HOST-BUSY
修复后    exit 2, note: 'web' ... running without one because --no-host was given
         Unknown command: web        ← 因为没加载插件，这是对的
```

重点不是它成功执行，而是**不再报 `HL-CLI-HOST-BUSY`**。

> 注意：这个命令在 `/var/lib/natter` 上会因权限报 `HL-CLI-STATE-DIR-UNUSABLE`（非 root 时）。要看 planner 行为，用 `--state-dir` 指向可写临时目录即可：
> ```bash
> /opt/natter/natter web status --json --no-host --state-dir /tmp/probe
> ```

## 6. 三个判定陷阱

### 6.1 别用 CLI 判断运行中宿主的状态

```bash
# 错：没有环境变量，secret 全部读不到
sudo /opt/natter/natter plugins list
# → 大量 missing-secret 假失败（本机实测 7 个，真实只有 3 个）

# 对：带环境，或直接看 health
sudo bash -c 'set -a; . /etc/natter/live.env; set +a; /opt/natter/natter plugins list'
curl -s http://127.0.0.1:5099/health | jq '.plugins'
```

secret 在 `/etc/natter/live.env`，只有 systemd 启动的进程才有。**判断真实状态一律用 `/health`。**

### 6.2 `wc -l` 不是插件数

```bash
natter plugins list | wc -l    # 19 —— 里面含 2 行表头 + 7 行错误明细
```

真实构成：2 行表头 + 10 行插件 + 7 行错误明细 = 19。

正确的数法：

```bash
natter plugins list 2>/dev/null | grep -cE '^natter\.'    # 10
```

### 6.3 插件目录不会被自动清理

`update-release.sh` 用 `cp -a`（复制不镜像），**从不删除插件目录**。

后果：插件改名/移除后，旧目录留着 → 两个目录同 plugin id → `duplicate-plugin-id` → 该插件 `Failed`。

```bash
# 部署前查差集
comm -23 \
  <(sudo ls -1 /opt/natter/plugins/ | grep -v staging-manifest.json | sort) \
  <(cd artifacts/publish/<release>/plugins && jq -r '.plugins[].name, "greetings", "metrics"' staging-manifest.json | sort)
# 预期无输出
```

> `greetings` / `metrics` 是 `dotnet publish` 直接产出的样例插件，**不在 manifest 里**。所以上面这条命令硬编码了它们，样例增减时要同步改。

## 8. 出问题时

| 症状 | 排查 |
| --- | --- |
| `status=degraded` | 查 `upstreams[].connected` 与 `providers[].available`，这是真故障 |
| 插件数不对 | §6.2 用 `grep -cE '^natter\.'` 数；注意 CLI 假失败 |
| `duplicate-plugin-id` | 幽灵目录，见 §6.3 |
| 消息发不出去 | `curl /health \| jq .upstreams`，看 `sendFailures` / `lastSendError` |
| 服务起不来 | `journalctl -u natter -n 50`；schema 迁移失败会在这里 |
| 需要回滚代码 | `sudo tar -C /opt -xzf /var/backups/natter/<ts>/natter.tar.gz` |

**回滚有约束**：代码可退，schema 不会退（v4→v7 已执行）。退回去后记忆检索会静默失效（返回空而非报错）。要彻底恢复需连库一起还原。
