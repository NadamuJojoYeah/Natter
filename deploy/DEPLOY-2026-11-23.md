## 5. 必须知道的风险：schema v7 迁移

### 实测：生产当前是 schema v4，这次会连续跑三段迁移

我从已部署的 `/opt/natter/Natter.Infrastructure.dll` 反查（SQL 字面量在 .NET 里是 UTF-16，需按 UTF-16 匹配）：

```text
memory_items    present     → v2 记忆表在，生产 ≥ v4
memory_fts      absent      → v5 的 FTS 未部署
text_index      absent      → v6 未部署
memory_entries  absent      → v7 未部署
```

所以部署后首次启动会依次执行：

| 版本 | 动作 | 是否改既有表 |
| --- | --- | --- |
| **v5** | 建 `memory_fts`（先试 trigram，失败降级 unicode61） | 新建 |
| **v6** | `ALTER TABLE memory_items ADD COLUMN text_index` + **DROP 并重建 `memory_fts`**（改列为 `text_index`，tokenizer 换 unicode61）+ 回填 | **改既有表** |
| **v7** | 建 5 张新表（`memory_entries` / `memory_turns` / `memory_profiles` / `memory_extraction_state` + FTS）+ 把 `memory_items` 数据搬过去 | 新建 + 搬数据 |

**三段一起跑，且 v6 会 `ALTER` 现有表、重建现有 FTS 索引。**

### 为什么有风险

- `SqliteSchema.Migrate` 在 store 构造期调用，**不包 try/catch** → 迁移抛异常则宿主起不来
- 迁移**只在合成库验证过**（3 条数据），未在真实生产库跑过
- `user_version` 一旦改到 7，**回滚代码不会回退 schema**

### 处理方式（二选一）

**方式 A（推荐）：先演练**

```bash
# 复制生产库到可读位置（服务可继续运行，WAL 模式下复制是安全的近似快照）
sudo cp /var/lib/natter/natter.db          /tmp/natter-probe.db
sudo cp /var/lib/natter/natter.db-wal      /tmp/natter-probe.db-wal 2>/dev/null || true
sudo chown $(whoami) /tmp/natter-probe.db*
```

然后把路径告诉我，我用当前产物在副本上跑一次迁移，核对：

```text
迁移前  user_version / memory_items 行数 / 各 kind 分布
迁移后  user_version / memory_entries 行数 / 是否有 kind 映射异常
```

确认无误再执行 §3。

**方式 B：直接上**

迁移失败时脚本会回滚代码，但 schema 已改。恢复方式：

```bash
sudo systemctl stop natter
sudo cp /var/backups/natter/<时间戳>/natter.db /var/lib/natter/natter.db
sudo systemctl start natter
```

（前提：备份包含 db 文件；若不含，需从 `sqlite3 .backup` 的副本恢复。）

### 5.2 陈旧插件目录（幽灵目录）

`update-release.sh` 用的是 `cp -a`（复制，**不镜像**），刻意保留 `scripts/` 与 `docs/`。代价是**它从不删除插件目录**。

后果：

```text
插件的目录名或 plugin id 一旦改变
旧目录留在 /opt/natter/plugins/ 下
→ 两个目录声明同一个 plugin id
→ duplicate-plugin-id
→ 该插件 Failed（不会静默，但会让功能失效）
```

**本次部署安全**：8 个 staging 目录名与生产现有的 3 个完全同名覆盖，不产生重复。

**但要注意一个已有的命名不一致**（不是这次要修的）：

```text
tier1/tier2 目录名     discord / deepseek / dingtalk / spark        （短名，既有约定）
feature  目录名        natter.tool.admin.webconsole / natter.feature.prompt.library / ...  （全 id，后来引入）
```

两种风格并存。**现在不要改**：生产上已经是 `natter.tool.admin.webconsole`，改名会留下旧目录 → 触发 `duplicate-plugin-id` → WebConsole 直接 Failed。

将来若要统一命名，必须配套删除旧目录：

```bash
sudo rm -rf /opt/natter/plugins/natter.tool.admin.webconsole
sudo deploy/update-release.sh --release <新产物>
sudo /opt/natter/natter plugins list | grep -c duplicate-plugin-id   # 必须为 0
```

## 8. 回滚

```bash
# 代码回滚（schema 不回退）
sudo systemctl stop natter
sudo cp -a /var/backups/natter/<时间戳>/. /opt/natter/
sudo chown -R root:root /opt/natter
sudo systemctl start natter
curl -s http://127.0.0.1:5099/health | jq -r '.status'
```

### 回滚有真实约束，不是「随时可退」

**代码可回退，schema 不会**。而且这次不是「只加表」：

```text
v6 已经 ALTER 了 memory_items（加 text_index 列）
v6 已经 DROP 并重建了 memory_fts（列从 text 改为 text_index）
```

所以回滚到 v4 代码之后的实际状态：

| 对象 | 回滚后 | 影响 |
| --- | --- | --- |
| `memory_items` | 多一个 `text_index` 列 | 无害，旧代码 SELECT 指定列，忽略它 |
| `memory_fts` | 结构已变为 `(memory_id, text_index)` | **旧代码的 FTS 查询按旧列名可能失效** → 记忆检索退化为无结果 |
| 新表 | 仍在库里 | 无害，旧代码不读 |
| `user_version` | 停在 7 | 旧代码的 `if (current < N)` 判断全部跳过，不会重复迁移 |

**结论**：代码回滚可行（宿主能起来），但**记忆检索功能会静默失效**（返回空而非报错）。这是最需要警惕的回滚副作用——它不报错。

若要彻底回到部署前，必须连库一起恢复：

```bash
sudo systemctl stop natter
sudo cp /var/backups/natter/<时间戳>/natter.db /var/lib/natter/natter.db
sudo rm -f /var/lib/natter/natter.db-wal /var/lib/natter/natter.db-shm
sudo systemctl start natter
```

因此**部署前必须确认备份包含 db 文件**：

```bash
sudo ls -la /var/backups/natter/<最新时间戳>/
# 若不含 natter.db，先手动备份：
sudo systemctl stop natter
sudo cp /var/lib/natter/natter.db /var/backups/natter/manual-$(date +%Y%m%dT%H%M%S)-natter.db
sudo systemctl start natter
```
